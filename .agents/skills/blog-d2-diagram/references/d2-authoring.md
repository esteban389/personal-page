# D2 authoring contract for the blog

Use this reference after a diagram has a clear reader question and source-backed
content. It intentionally covers the blog-specific decisions that official D2
documentation cannot make for us.

## Toolchain contract

- Renderer: D2 CLI `0.9.0`.
- Primary output: SVG committed under the blog's stable public article-image
  path.
- Default layout: ELK. Dagre is allowed only after comparing the result.
- Light theme: `0`; dark theme: `200`; padding: `32`; version metadata omitted.
- The render helper owns those flags. Do not duplicate them in each `.d2` file.
- Pinning is essential: D2 `0.8.2` deliberately changed Dagre and ELK geometry,
  and later versions may do so again. Upgrade by regenerating and visually
  reviewing every stored SVG in one explicit change.
- D2 `0.9.0` also bundles TALA, but the helper deliberately limits output to ELK
  and Dagre until a concrete article demonstrates that a third layout improves
  clarity enough to justify another reviewed rendering mode.

The blog uses author-time rendering rather than an Astro Markdown plugin. This
keeps the production build independent of D2, makes SVG changes reviewable, and
produces a portable asset with a stable public URL. D2's upstream JavaScript
changelog now records a `dispose()` fix for its former worker-lifecycle problem,
although package availability must be verified before relying on it.
Pre-rendering is a workflow choice rather than a claim that build integration is
impossible.

## Choosing a D2 form

| Reader question                                              | Preferred form                |
| ------------------------------------------------------------ | ----------------------------- |
| Which component owns what, and how do they connect?          | Container or architecture map |
| What happens in time, especially around retries or failures? | Sequence diagram              |
| How can one entity move between states?                      | State graph                   |
| Where does data or responsibility cross a boundary?          | Directed flow                 |
| Which path follows from each condition?                      | Decision flow                 |
| How are concepts grouped by responsibility?                  | Grouped relationship map      |

Use a Markdown table for exact repeated fields, a chart for numeric magnitude or
trend, a screenshot for actual UI state, and a code block when syntax is the
subject.

## Source conventions

- Make semantic IDs stable and language-neutral; put localized text in labels.
- Declare important nodes before connecting them. Use containers to express real
  ownership or trust boundaries, not visual decoration.
- Use `direction: right` for left-to-right flows and `direction: down` when the
  article reads as a vertical lifecycle. Let autolayout do the rest.
- In `shape: sequence_diagram`, source order is presentation order. Declare
  actors first when their order matters.
- Label connections with actions or data, not vague words such as “handles.”
- Keep API names, class names, headers, and protocol tokens unchanged across
  locales unless they truly have localized names.
- Use comments for evidence locators or unresolved authoring decisions; do not
  render uncertainty as fact.
- Prefer one diagram that answers one question. Split a dense visual when labels
  become tiny, edges cross repeatedly, or two independent explanations compete.

Minimal flow example:

```d2
direction: right

student: Student service
users: Users service
database: Users database {
  shape: cylinder
}

student -> users: create user
users -> database: commit
users -> student: user ID
```

Minimal sequence example:

```d2
flow: {
  shape: sequence_diagram

  client: Client
  api: API
  worker: Worker

  client -> api: submit
  api -> worker: enqueue
  worker -> api: result
  api -> client: respond
}
```

## Styling and reproducibility

- Start with the official theme instead of styling every object.
- The blog accent is `#197ca8` in light mode and `#74c7dc` in dark mode. Use it
  sparingly for the main path or focal boundary; retain theme contrast for text.
- Pair semantic color with a label, dash, arrowhead, or shape. Include a legend
  when more than one non-obvious encoding exists; localize its title and labels.
- Avoid sketch mode by default. A hand-drawn texture is an editorial choice, not
  a shortcut to make an autogenerated diagram feel human.
- Avoid remote icons, remote images, animations, tooltips, and links. Remote
  resources weaken reproducibility, while SVG loaded as an `<img>` does not keep
  D2 link interactivity. Put necessary information in the visible diagram and
  article.
- Relative D2 imports resolve from the importing source file. Use imports only
  for genuinely shared, stable structure or styles; a shared import can cause
  broad output changes.

## Localization

For translated posts, use paired source and output files:

```text
apps/blog/diagrams/<article>/request-flow.en.d2
apps/blog/diagrams/<article>/request-flow.es.d2
apps/blog/public/images/posts/<article>/request-flow.en.svg
apps/blog/public/images/posts/<article>/request-flow.es.svg
```

Keep the same semantic keys and topology when both posts make the same claim.
Translate visible labels, legend text, caption, and alt text. If the translated
article differs materially, the diagram may differ too; `translationKey` does not
require identical content.

## Embedding and accessibility

Use a root-relative URL while authoring and previewing the blog:

```markdown
![Alt text describing the diagram's explanatory point](/images/posts/<article>/<diagram>.en.svg)
_Caption that tells the reader why the diagram matters._
```

```markdown
![Texto alternativo que describe el punto del diagrama](/images/posts/<article>/<diagram>.es.svg)
_Leyenda que explica por qué importa el diagrama._
```

Alt text should communicate the diagram's purpose and essential relationship.
For a complex visual, provide the full explanation in adjacent prose or a list so
it is available to every reader. Verify that no critical distinction relies only
on color and that labels remain readable on a narrow viewport.

The SVG's adaptive D2 dark theme follows the browser or embedding color scheme;
the blog also has a manual `data-theme` toggle. Until the site has a dedicated
diagram component that explicitly synchronizes those modes, inspect both manual
themes and do not assume they always match the operating-system preference.

### Syndication boundary

The current DEV syndication script rejects relative inline image URLs, including
root-relative `/images/...` paths. After the blog post and SVG are deployed, a
post intended for DEV must use the stable absolute form before syndication:

```markdown
![Alt text](https://blog.estebanmurcia.dev/images/posts/<article>/<diagram>.en.svg)
```

Run the normal syndication dry run afterward. Medium imports the live canonical
page, but its image rendering must still be checked during the manual import.
Do not assume either external platform preserves SVG behavior, adaptive dark
themes, captions, or dimensions exactly; preview both destinations before
publishing. A future syndication URL-rewrite step could remove this manual source
change, but it does not exist in the repository today.

## Renderer availability

The helper expects D2 CLI `0.9.0` on `PATH`. If it is unavailable, do not silently
install software. Use the official `v0.9.0` release archive and its `SHA256SUMS`
file after authorization, or point the helper at a reviewed binary:

```bash
D2_BIN=/path/to/d2-v0.9.0/bin/d2 \
  node .agents/skills/blog-d2-diagram/scripts/render.mjs check \
  apps/blog/diagrams/<article>/<diagram>.<lang>.d2 \
  apps/blog/public/images/posts/<article>/<diagram>.<lang>.svg
```

## Authoring loop

Run from the repository root:

```bash
d2 version
d2 fmt apps/blog/diagrams/<article>/<diagram>.<lang>.d2
node .agents/skills/blog-d2-diagram/scripts/render.mjs write \
  apps/blog/diagrams/<article>/<diagram>.<lang>.d2 \
  apps/blog/public/images/posts/<article>/<diagram>.<lang>.svg
```

After embedding, run the content validation from the repository instructions and
inspect the generated post route. The helper's `check` mode is suitable for CI if
the diagram workflow is later adopted as a repository command.
